# 城の領主・プレイヤー家臣・本拠移転・加入順の継承

## 公開の所属と個人の戦役

通常の開始城123城について、一城一人の公開領主と、加入順に並ぶプレイヤー家臣をサーバーで管理する。江戸・京都御所・二条・大坂・名古屋・鹿児島の特別な拠点制度はこの名簿の対象外。所持武将としての「家臣」とは別の制度である。

全城に領主がいても、参加者は城を選んで家臣として入れる。空き城がある場合も、領主のいる城へ家臣として参加できる。領主交代は公開の所属だけを変更し、別プレイヤーの保存・兵・資源・武将・購入済み外観を移さない。新しい物語として入城し直す操作は、通常の新規戦役と同じく確認後に個人の進行を新しくする。

## 家臣数による開始城の補正

現在の領主が通常の開始城を領有している間、名簿の家臣1人につきその城の初期能力の50%を加算する。1人あたり最大耐久5,000、防衛時の守備兵600人分、兵収容上限250、月間の基礎生産は金銭50・兵糧85・木材20・石材15。防衛の加算は戦闘計算で適用し、移送や出陣に利用できる実兵の数は別に管理する。

## 一般プレイヤーの本拠移転

城下町から、現在の本拠以外の通常城を選んで何度でも移転できる。移転先が空席なら領主、すでに領主がいれば加入順の末尾に家臣として入る。領主が退去した城では、残った家臣のうち最先の有資格者が領主を継ぐ。ほかの住人の所領・武将・資産は移転者の戦役から独立している。

個人の戦役を新たに開始し、所領・施設・研究を初期状態に戻す。兵・資源・勾玉は開始時の上限と移転前の残高の小さい方が新しい残高になる。所持武将と育成、領主名、購入済みの品は引き継ぐ。移転回数や受付間隔に個別の上限を設けない。

## API

経路には `/api/v1` を前に付ける。

| 経路 | 内容 |
| --- | --- |
| `GET /castles/residency` | 123城の空き状況、領主、家臣数、名簿の版、接続者自身の所属。未接続でも公開一覧を取得できる。 |
| `GET /castles/residency?castleId=...&limit=50&cursor=...` | 指定城の領主、家臣、継承順、次ページのcursor、直近の継承履歴を追加する。 |
| `POST /castles/residency/start` | 操作端末と保存の版を確認し、領主または家臣として新しい戦役を開始する。 |
| `POST /castles/residency/relocate` | 現在の個人戦役から通常城へ移転する。到着時の空席または現領主を照合し、サーバーが身分を決める。 |

移転の本文は `deviceId,revision,requestId,castleId`。接続者の保存と所属名簿を同じトランザクションで更新する。再送には最初の要求と同じ `requestId` を使う。通信が途切れたときは `POST /castles/residency/relocate?receipt=1` で確定済みの結果を照会できる。照会だけでは新たな移転を実行しない。

入城の本文は `deviceId,revision,requestId,castleId,mode,clan,difficulty`。`mode` は `lord` または `retainer`。サーバーが開始セーブを作り、所属の更新と同じトランザクションで保存する。応答には通常の同期情報と `admission` を含める。重複要求は保存の版・端末lease・現在の空き状況の検査より前に記録を照合し、同じ要求を二重に確定しない。

`residency` は `castleId,castleName,role,retainerCount,joinedAt,eligible,successionPosition,lord,lordPlayerId,lordEpoch,revision` を含む。領主の `successionPosition` は0、継承可能な家臣は1以上、現在継げない家臣はnull。同期応答と `/field/me` にも本人の所属と `residencyRevision` を含める。画面は名簿の版を単調に取り込み、古い応答で昇格を巻き戻さない。

## 領主を継ぐ条件

現在の公開領主が、登録された所属城の本拠防衛で敗れた場合、継承できる家臣のうち最も早く加入した人を次の領主にする。接続中かどうかは判定に使わない。敗れた領主は列の最後へ移る。同じ城で新しい戦役を始めても、本人の加入順は維持する。

対象は共通フィールドの本拠戦、同盟集結軍による本拠戦、派遣部隊の反撃、サーバーが証明した通常CPU勢力による本拠陥落。支拠点だけの敗北、出陣先での敗北、野良兵戦、期間限定合戦、共有天下統一大会では領主を交代しない。家臣がいない場合、領有を移さない対人襲撃では現在の領主を維持し、実際に本拠を失うCPU戦では空席にする。

継承候補は、利用可能な一般プレイヤーで、個人の戦役が続いており、登録された所属城を自身の勢力が本拠として保持している人。対象外の家臣は名簿に残し、継承順をnullにして次の候補へ進む。同じ本拠の新しい戦役で復帰すると、元の加入順から再び対象になる。運営・スタッフへの任命や利用停止で通常城の資格を失った人は名簿から除き、領主席は次の候補または空席へ更新する。

## 競合・再送・到着時の整合性

加入順はサーバーの単調な連番で決める。最後の空席への同時入城も、保存の版・所属・領主の世代を条件に、一つだけ確定する。継承は戦果の最初の確定条件に現在の領主世代と最先頭の有資格家臣を含め、戦果・資産・名簿・通知を一つのD1バッチで更新する。途中で候補が移動した場合は戦果全体を再確認し、敗北だけを確定して継承を失うことを防ぐ。

出陣時に対象の `castleId,lordPlayerId,lordEpoch` を保存する。到着までに領主が交代した攻撃・偵察・派遣は、新領主へ付け替えず中止して兵と費用を一度だけ返す。家臣が増えても領主世代は変えない。同じ城に所属する領主・家臣同士の攻撃は出陣時と到着時の両方で禁止する。すでに駐留している生存部隊は自動回収せず、帰還操作が可能な状態を保つ。

CPU戦の証明には、共有エンジンの `takeHomeDefenseLosses()` が返す一時イベントを使う。この記録はセーブに保存せず、インポートや戦報文字列から復元しない。通常の保存アップロードでは、前回の確定済みセーブと共通時計からCPU進行を再実行する。登録された本拠を、アップロードした `home`・`gameOver`・領有フラグだけで変更しない。別の城で新しい物語を始める場合は入城APIを使う。

領主就任時の共通経過時間を記録し、就任前の留守中の敗北で新領主を即座に降格させない。過去の本拠陥落を遅れて再生した場合は、本拠・領有・継続状態を現在の任期に合わせ、資産を複製しない。この補正にも任期の確定条件を付け、同時昇格と保存が競合した場合は再確認する。

移転の確定で旧戦役の進軍・派遣・歩行セッションを終了する。同盟から預かった兵・補給は同盟の清算方法に従い、ほかの領主が派遣した援軍はその派遣元へ戻せる。成立済みの取引や購入品の権利はアカウントに残る。

## 移行と配備

`0029_castle_residency.sql` と移行ジャーナルを同じリリースに含める。城・家臣・連番・入城要求・継承・CPU再生位置の台帳、および派遣の対象任期を保存する列を追加する。既存の保存を初めて名簿へ取り込むときは、アカウント登録日時とIDで決定的に並べ、最も早い有資格者を領主とする。他の住人は家臣に入り、個人の保存を維持する。

`0030_residency_relocations.sql` は移転で終了した戦役を記録し、古い端末がその保存を再送して移転前の資産へ戻すことを防ぐ。

ブラウザは `residency.js` を共通時計より後、戦闘画面・アプリより前に読み込み、`residency.css` とともに同じリリースのService Workerへ登録する。API配備確認は `/api/v1/health` の `version: "4.9.4"`、`features.residencyRelocation: true`、`status: "ready"`。既存の公開範囲・環境変数・DB/R2を維持する。

## 検証

主な自動検証は、フロントエンドの `tests/test-residency-engine.cjs`、`tests/test-residency-ui.cjs`、`tests/test-residency-bridge.cjs` と、Workerの `scripts/test-residency.mjs`、`scripts/test-residency-covert.mjs`、`scripts/test-residency-tenure.mjs`。空席競合、満城、加入順、オフライン継承、適格性、保存の偽装、戦果の再送、候補の移動、古い対象への到着、就任前のCPU敗北を検証する。距離行軍の既存テストも、異なる所属城の有効な相手を使って継続する。

ブラウザの操作確認は隔離したDBと実Worker APIを接続し、満城からの新規家臣入城、継承順、領主への昇格、プロフィールと城下町への反映、狭い画面での名簿を確認する。本番のプレイヤーをテスト攻撃・登録・役職変更に使わない。


## v5.12.0 の追放とサブ運営

運営が領主を追放した場合は、`lord_user_id` を空にし、本人の所属だけを削除する。残る家臣は所属と加入順を維持し、追放を契機とした自動継承を行わない。家臣の追放では本人の所属だけを削除する。通常の防衛敗北による継承とは別の操作である。

鹿児島城はサブ運営の固定拠点となり、通常城の名簿・入城・移転から除外する。主運営の任命で元の城を退去し、解雇時は元の通常城が空席なら領主、埋まっていれば家臣として復帰する。役職変更と所属・セーブ変更は同一トランザクションで確定する。鹿児島城には家臣を受け付けない。
