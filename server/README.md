## 配置と移行

- `index.js`・`game-engine.js`・`game-officers.js`・`game-runtime.js`・`letters.js`・`trade.js`・`moderation.js`・`premium.js` をAPIプロジェクトの `worker/` に配置します。ビルドでは武将データ、共通エンジン、書状、交易、運営管理、有料外観、APIを結合し、単一のWorker ESMを `dist/server/index.js` に出力します。この参照フォルダー内ではモジュールを隣接させたまま、テストからESMとして直接読み込めます。
- `drizzle/0000_social.sql` から `0013_premium_purchases.sql` までの移行と `drizzle/meta/_journal.json` を、APIプロジェクトのルートに維持します。0005は写真のメタデータ、0006はギルド役職・共有資産・操作記録、0007は周回の保存位置・報酬受取記録・公開達成通知、0008は駿府城の共同成長・着工記録・任命前の個人拠点、0009は歩行計測、0010は書状、0011は個人間の交易、0012はBAN状態・操作記録・投稿更新番号、0013は有料商品の検証済み決済記録・外観・保留確認の監査を追加します。
- hostingの論理バインディングは `d1: "DB"`、`r2: "BUCKET"`。static設定は不要です。
- 初回運営キーは秘密の実行時環境変数 `SENGOKU_ADMIN_KEY` にだけ設定します。
- 別Originのフロントエンドは `SENGOKU_ALLOWED_ORIGINS` に正確なOriginをカンマ区切りで設定します。

適用済みの移行ファイルは編集せず、新しいSQLファイルを追加します。リクエストハンドラーはDDLを実行しません。共通時計のテーブルは移行で作成し、時計を初めて読む際に一行の初期値を排他的に作成します。

## 保存と同期

ユーザー、トークンのハッシュ、ギルド、フレンド、メッセージ、お知らせ、郵便、ギフト受取記録、クラウドセーブ、操作権、端末連携コード、接続状況、共通時計をD1へ保存します。

同じ領主IDにつき一つの操作権リースを持ち、セーブの版番号による比較更新を行います。同時操作による上書きを防ぎ、別端末へ切り替えた場合は古い端末の書き込みを拒否します。連携コードは一回限り・10分間有効、サーバーにはハッシュだけを保存します。連携後には新しい端末用のトークンを発行します。

運営権限はユーザー行、スタッフ権限は現在の任命記録で確認します。江戸城・德川家康Uは運営だけ、駿府城はスタッフだけが所持できます。旧バージョンの役職と合わない保存は、通常の本拠と成長を保てる形に移行します。運営のU復元は重複しません。

城郭の強化上限は、江戸・駿府がLv.64、二条・大坂・名古屋がLv.48、通常城がLv.32です。保存、普請、公開フィールド、費用と効果を同じ上限で扱います。城下町施設はLv.32を維持します。

運営とスタッフの家名は「德川家」です。家名から役職を判定せず、江戸城・専用Uは運営資格、駿府城は現在のスタッフ資格で確認します。任命前の個人の家名はサーバーのバックアップを正とし、解任後の本拠・所有城・公開プロフィールへ復帰させます。通常の「徳川家」は一般プレイヤーが利用できます。

## ウォーキング・書状・軍師AI・連続普請（Ver.3.8.0）

`0009_walking_rewards.sql` は領主ごとの歩行累計、計測セッション、精算履歴を追加します。1検知歩で金銭・兵糧・木材・石材・勾玉へ各2を付与し、現在の操作端末・保存revision・キャンペーン・セッションを確認した同じトランザクションで記録します。再送は既存の受領を返します。歩調の上限は現実のサーバー時刻で確認し、ゲーム内の時計停止や倍速は適用しません。モーション値そのものをサーバーが物理的な歩行として証明する機能ではありません。

`0010_base_letters.sql` は本拠から送る書状の会話・本文・送信履歴・閲覧履歴を追加します。個人宛ては当事者二人、ギルド宛ては送り主と現在の所属メンバーだけが閲覧・返信できます。外部書状はギルド内部チャットとは別です。宛先の現在の所属と返信権限は書込時にも確認し、同じ送信番号の再試行で本文を重複保存しません。

施設の連続普請は同一施設の予約列を1枠として扱い、資源と指令を予約時に支払います。一般領主の保存とスタッフ共同拠点の両方で段階順・上限・時間を検証します。軍師AIは共通のゲームエンジンで作戦の解析・候補評価・直前検証を行い、フロントエンドの表示状態・操作権・時計・保存状態を確認しながら1件ずつ実行します。

詳細なAPIと入力・出力は `API_CONTRACT.md` を参照してください。

セーブ形式は厳密に検証しますが、すべての戦闘・内政をサーバーだけで計算する方式ではありません。ローカル編集可能なゲームの全経済に対する不正防止を保証するものではありません。

システム便の贈り物は、金・兵糧・木材・石材と勾玉に対応します。`gift.magatama` は任意の0〜1,000,000の整数で、勾玉のみの添付も可能です。省略・0は従来の4資源のJSON形式を維持し、過去の送信要求の再送と互換性を保ちます。受取クライアントは勾玉を `state.magatama` に加算し、同じ保存で受取台帳を更新します。保存失敗時は資産と台帳の両方を戻し、同じ記録で再試行できます。

## 他領主との交易（Ver.3.10.0）

`0011_player_trades.sql` は、金銭・兵糧・木材・石材・勾玉の輸出入を扱う提案、実行記録、受取台帳を追加します。相手は領主IDで指定し、家名や城IDが同じでも別の領主として扱います。提供資産は提案時に送り主の保存から差し引いて預かります。相手の承認時に、承認者自身の保存から対価を差し引き、提供資産を加えます。対価なしの無償輸出もできます。

送り主への対価と、取消・拒否による返金は独立した受取台帳に残し、本人が「受け取る」を実行したときにだけ本人の保存へ加算します。相手の保存・revision・操作権は一切変更しません。相手がオンラインで未保存の進行を持っていても、その進行を交易によって巻き戻すことがありません。資産上限を超える場合は全額受取を拒否し、台帳を残します。切り捨てや資産消失はありません。

提案・承認・取消・拒否・受取はすべて現在の操作端末と保存revisionを検証します。各資産は1件あたり最大1,000,000、保管上限は999,999,999、承認待ちの送信は20件までです。指令・手数料は不要で、共通時計が停止中でも操作できます。成功したrequestIdと意味上の内容を永続化し、同一要求の再送では同じ実行記録と最新の同期結果を返します。同時の承認と取消、二重受取、途中失敗を、条件付き記録とD1バッチでまとめて処理します。既存のメールギフト適用関数は使いません。

閲覧できるのは当事者二人だけです。提案・対価・返金はギルド離脱、役職変更、周回、新しい物語を越えて同じ領主IDに保持されます。各APIとDTOは `API_CONTRACT.md` の「Player trades」を参照してください。

`GET /trades` の一覧は `box=incoming`（受信）、`outgoing`（送信）、`history`（両方向の履歴）、`claimable`（本人の受取待ち）を選べます。受取待ちは未受取の対価・返金だけを作成日時の新しい順に返すため、履歴の21件目以降に残る古い資産も直接探せます。全一覧で同じ件数制限・ページング・集計形式を使い、受取済みの記録は次の受取待ち一覧から外れます。

## 運営によるBAN・解除（Ver.3.11.0）

現在の `settings.adminUserId` 本人だけが、領主名・完全な公開IDで対象を探し、削除対象件数を確認してBANできます。スタッフや一般領主、入力JSONの権限指定には管理権を与えません。自分・運営本人は対象にできません。BAN中の一覧から解除でき、解除後は同じ領主ID・既存の接続トークンで再利用できます。

BANは一つのD1バッチで、本人が送った世界・ギルド・フレンド・運営チャットと個人・ギルド書状の本文行を削除し、接続表示・操作権・未使用の連携コードを停止します。計測中の歩行セッションも終了し、確定済みの歩数や報酬は保持します。本人が関係する承認待ちの交易を取消し、提供資産は元の送り主の受取待ち台帳へ返します。他人の本文、保存データ、資産、ギルド所属・役職、確定済み取引は削除しません。解除しても消した本文は戻りません。

全端末の認証済み操作を `ACCOUNT_BANNED` で拒否し、BANと解除で進む認証世代をSQL更新時にも照合します。処理中の投稿・保存がBAN後に書き戻ったり、BAN→解除の間を跨いだ古い要求が通ったりすることを防ぎます。解除後の操作権と歩行計測は新たに開始します。公開の検索・接続一覧・共有地図・達成通知・写真はBAN中の対象を表示しません。

BANによる本文削除で `contentRevision` が進みます。チャット・書状はこの番号を返し、古い番号の差分取得には `reset:true` と最新ページを返します。クライアントは削除前の表示キャッシュを破棄して置き換えます。監査記録には運営・対象・操作番号・時刻・削除件数を保存し、削除した本文のコピーは保存しません。同じ要求の再送は元の記録を返すだけで再BAN・再解除を行いません。

APIの入力と出力は `API_CONTRACT.md` の「Account moderation」を参照してください。公開確認は `GET /health` / `GET /config` の `version:"3.11.0"` と `features.moderation:true` を読み取り、実プレイヤーのBANや投稿削除は行いません。

## 共通のループ時計

`GET /api/v1/world-clock` は認証不要です。サーバーの経過時間、進行中かどうか、速度、設定の版番号、サーバー時刻を返します。`PATCH` は運営のみ、版番号が一致した場合にだけ変更します。クライアントが任意の年月を送って世界時計を巻き戻す操作は受け付けません。

暦は672か月で一周し、1560年1月から1615年12月の後に次の周へ進みます。内部の経過ミリ秒は増え続けます。停止・再開や速度変更では、それまでに経過した時間を確定してから新しい設定へ切り替えます。

新しいセーブは `state.worldClock` に適用済みの経過時間を保存します。年月・月内秒との整合性と、サーバーより過度に未来でないことを検証します。移行済みのクラウドセーブを、時計位置のない旧形式で上書きすることはできません。古い有効な保存位置からの再接続は許容します。周回の境界は共通エンジンを使ってサーバー側で確定し、それ以外の進行は操作端末が共通時刻へ追いつきます。

## v3.6 — 拠点の集計・報酬・御触書

`0007_world_cycles.sql` は `player_saves` に周回の保存位置と最初の本拠を追加し、`cycle_receipts` と `achievement_events` を作成します。適用済みの0000〜0006は変更せず、追加済みのjournalと一緒に維持してください。

暦の境界では、その時点で所有する本拠以外の城1つにつき、勾玉100・金銭1,000・兵糧1,000を一度だけ加算します。通常の所持上限は適用されます。追加の領地は初期配置へ戻し、最初の本拠を復元します。運営は德川家・江戸城・専用Uを維持します。本拠の城郭レベル、施設、武将、技術、資源、ギルドと共有金庫は引き継ぎ、本拠以外の城郭拡張と前の区切りから続く同盟・偵察を終了します。導入時点より前の周回報酬は遡って付与しません。

操作端末は境界の1ミリ秒前まで進めた保存を確定してから `POST /api/v1/sync/settle` を呼びます。通常の読み取りは、有効な操作権を持つ端末の未保存操作を先回りして集計しません。切断済みの保存は読み取り時に段階的に追いつきます。保存の版、操作権、共通時計、運営資格を更新時にも確認し、セーブ・報酬受取記録・通知を一つのD1バッチで確定します。再送や同時処理による重複付与、途中失敗時の部分的な加算を防ぎます。

公開の `GET /api/v1/achievements` は、受け入れ済みの保存やサーバーで確定した進行から、「どの領主が何を達成したか」を新しい順に返します。城の占領、領有数の節目、施設・研究の成長、任務達成、統一、占領報酬などが対象です。最初に読み込んだ保存から過去の通知を作ることはありません。通知キーで再送をまとめ、非公開のログイン履歴、端末情報、トークン、資産総額、金庫台帳は含めません。

## 総合評価と位階

全プレイヤーへ、領地・城郭、完成済み施設、所持武将、軍団と奉行、研究、威信・攻城の勝利実績、歩行進捗を合計した10万点満点の総合評価と、無位から正一位まで17段階の位階を表示します。位階は称号であり、運営・スタッフ・ギルドの権限には影響しません。共通の `GameEngine.publicEvaluation` を使い、クライアントから送られた評価値や称号は採用しません。

公開DTOは基本を `evaluation` とし、盟主・戦報・書状等は表示する人物に対応した評価を添えます。チャットと書状の読み取りは `playerEvaluations:[{playerId,evaluation}]` も返し、追加発言がなくても表示済みの参加者の称号を更新できます。対象はその部屋・書状の参加者と最近の発言者に限り、非公開の会話を越えて取得しません。詳細なフィールド名は `API_CONTRACT.md` に記載しています。

評価は最新の正規保存に現在の役職、完成した共同施設、未反映の周回を読み取り専用で投影します。評価の取得だけで月次進行・報酬付与・保存・編成変更はしません。未保存の領主は0点・無位ですが、保存を正常に読めない場合や取得できない過去の人物は `null` とし、未確認の位階を表示しません。同じ応答内の領主はまとめて一度ずつ計算し、DBの移行や称号キャッシュは追加しません。`test-evaluation.mjs` で役職・共有拠点・周回・差分更新・履歴・100人一覧の重複計算防止を検証します。

## サポートスタッフ

スタッフは `staff_members` に保存し、`isStaff` と `isAdmin` を区別します。主運営のみ `GET/POST /admin/staff` を使用でき、登録済みの対象領主を任命・解任できます。役職変更と再送台帳は同じトランザクションで確定します。解任後に古い任命要求を再送しても、役職を巻き戻しません。

スタッフの追加権限は、駿府城の共同普請、運営チャットの閲覧・送信、直近24時間のログイン・接続履歴の閲覧です。江戸城・德川家康U・共通時計の管理・告知・配布・スタッフ管理には運営権限を要求します。運営とスタッフを兼ねる場合は運営の德川家・江戸城を優先します。運営チャットとログイン履歴はSQLでも参加権限を再確認し、解除済みのトークンで利用できないようにします。任命・解任で領主IDや認証トークンを作り直すことはありません。

### 駿府城の共同成長

駿府城は占領できない固定本拠です。対人の報酬戦は受け付け、実際の共有施設を守備計算に使います。相手が勝利しても守備側の兵・資源・施設は減らしません。城郭レベル、城下町の64施設、進行中の普請をサーバーで一つに管理し、全スタッフが共有します。武将・軍団・研究・奉行・資源残高は個人ごとに保持し、着工者が自分の資源と指令を使います。共有した成長は周回を越えて残ります。

`GET /staff/base` と同期応答の `staffBase` は個人セーブとは独立した版番号を持ちます。`POST /staff/base/upgrade` は個人セーブの版、共同拠点の版、端末の操作権、現在のスタッフ資格を確認し、個人負担・共同の着工・再送記録を一緒に確定します。クライアントのインポートや通常保存から共有レベルを書き換えることはできません。

共有施設は実行中のゲームへ投影し、個人セーブの施設とは分けて保存します。任命前の個人拠点をサーバーに記録し、解任後は個人の進行を維持して通常の本拠へ戻します。共有普請の完成時刻を使って留守中の進行を区切り、新しい施設効果を完成前の期間へさかのぼって加算しません。

## 領主アイコンとギルド資産

領主アイコンは本人だけが登録・削除できます。ブラウザー側で切り抜いた256×256 JPEGを受け取り、Workerで48KiBの上限と構造を検証し、EXIF・GPS・コメント等を除去します。画像本体はR2、現在版のメタデータはD1へ保存します。画像更新中の読み取り・削除競合を検証し、古い画像や削除済み画像は404で返します。

ギルドは盟主・副盟主・メンバーの役職を持ちます。5種類の共有資産の移動は、現在の所属、操作端末、プレイヤー保存の版、金庫と共通時計の版をトランザクション内で検証し、金庫と所持資産を一緒に更新します。成功済みrequestIdを保存し、応答を失った後の再送を再加算しません。台帳は所属メンバーだけが取得できます。公開ランキングは総威信・人数・領有城を集計し、金庫の残高や台帳を含めません。

追加検証は `test-recent-logins.mjs`、`test-avatars.mjs`、`test-avatar-jpeg.mjs`、`test-clans.mjs`、`test-guild-assets.mjs`、`test-guild-roles.mjs` です。JPEGの復号比較はPythonのPillowも使用します。

## 実装上の境界

SQL値はバインドします。各prepareは一つのSQL文、複数操作のトランザクションは `DB.batch()` を使います。セーブとギフトの受取台帳はクライアントでも同時に永続化し、再送時の重複を防ぎます。

Cookieは使用せず、非公開APIにはゲームのBearerトークンが必要です。CORSは正確な許可Originだけに応答し、資格情報付きワイルドカードを使いません。秘密の環境変数、運営キー、生トークンをログに出力しません。
