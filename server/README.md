## v5.10.0 サーバー招集・朝昼夜の勾玉・支払い期間ごとの外観

`0040_paid_rewards.sql` と `rewards.js` を追加します。接続中の通常招集は1回・10回ともサーバーの暗号学的乱数で抽選し、勾玉消費・最終獲得・重複返還・操作記録を同じD1トランザクションで確定します。1回300、10回2,700勾玉、既存のランク確率と武将内の等確率は維持します。

税込480円の `reroll-pass-30d` は自動更新のない30実日券です。有効中は1日3件まで、単発招集1件につき1度引き直し、元の絵巻と新しい絵巻から1枚を確定できます。初回300勾玉を一度消費し、候補のままでは家臣・重複返還を付与しません。保留はサーバーに残るので、切断後も選択を再開できます。10連全体の引き直しはありません。この購入は獲得できる武将に影響するゲーム上の優遇です。

朝05:00–11:59、昼12:00–17:59、夜18:00–翌04:59に各30勾玉を受け取れます。ログイン報酬と引き直し回数は日本時間05:00に日次更新し、ゲーム内の月・端末時計・午前0時では再付与しません。勾玉上限では受取枠を残し、一部だけ空いている場合は実際に入った額を記録します。

月額780円サポーターは、支払い済み請求期間ごとに季節の3種類から外観1点を永久に選べます。導入時に有効な支払い期間も対象で、導入前に終了した全履歴をまとめて付与しません。解約後も選択した外観は残り、返金・異議申立て等は既存の金融記録で処理します。同一期間の再通知・重複請求記録で選択権は増えません。同月3期間分がある場合の新規購入は停止します。古い決済画面から例外的に4件目が支払われた場合は次の空いている月の外観3点を割り当て、支払済みの選択権を失わせません。

### セーブ復元と計測の境界

新しい報酬を利用した領主の招集履歴・所持絵巻・勾玉増分は、以降の同期でサーバー保存と照合します。別のcampaign IDを付けても回避できません。正規の新しい物語は作成でき、既知の物語は退避した最新の確定状態に照合して復帰できます。招集の確定前まで巻き戻す古いバックアップや未確認の進行済み保存は `SERVER_REWARDS_REQUIRED` となり、最新クラウド保存の読み込みが必要です。保留中は先に1枚を確定してください。これは既存のCPU戦・内政の全操作をサーバーで再計算する仕組みではありません。

ショップの表示・購入操作は件数と接続アカウントのユニーク数を別々に保存します。運営専用 `/admin/premium/metrics` は、従来の件数・ログイン報酬再受取率に加え、全9商品の円建て有効支払い合計、サポーター翌期間更新率、無料・課金別の接続アカウント翌日／30日後再訪率を返します。表示期間は14・30・60・90日で、30日後再訪も確認できるよう初期値は60日です。

追加移行 `0041_player_activity_metrics.sql` はテーブルと索引の追加だけです。過去の活動や支払確認日時を作りません。接続再訪の観測開始時刻は最初に成功した認証済みゲームAPI要求で固定し、初回観測時点で有効な確認済み支払い履歴があるかによって無料／課金を固定します。後日の購入・返金でその分類を変更しません。初回観測は登録日ではありません。翌日・30日後が丸一日終了したコホートだけを評価し、母数ゼロの率は未計測（null）にします。日次記録は主キーで重複を防ぎ、同日のポーリングはキャッシュで記録処理を省きます。記録失敗でゲームの成功操作をエラーにしません。

売上欄は一致したStripeチャージ実額を決済単位で集計した「確認済み有効支払い合計（税込）」です。決済作成日時を日本時間05:00で区切ります。返金・異議申立て・保留等の利用権を確認できない決済は全額を除外欄へ分け、未確認の支払いは含めません。商品を特定できない相関矛盾も別枠にします。旧台帳には正確な返金額や決済手数料がないため、純売上とは表記しません。

サポーターの更新率は、支払確認の計測開始後に終了し7日間の猶予が終わった期間を分母に、同じ契約の連続する翌期間をその猶予内に照合確認した割合です。通常の解約も分母に含めます。支払確認時刻は新台帳へ最初の観測時刻として固定し、古い決済作成時刻から推定しません。閲覧→購入率も、閲覧後に決済が作成され、照合確認されたアカウントを数え、過去の購入を今回初観測しただけでは増やしません。

運営の集計閲覧は記録を作らず、匿名・未接続のプレイや計測開始以前は対象外です。接続再訪率を全プレイヤーの継続率、宣伝が原因で増えた人数として扱わないでください。観測前や観測途中の数値は補完しません。

ローカル検証: `node server/test-rewards.mjs` と `node server/test-premium-metrics.mjs`。模擬Stripe署名・金融記録とメモリ上のSQLiteだけを使い、外部通信・実決済・本番データ変更はありません。

## v5.4.0 旧セーブの時計移行と京都御所の個人工事

体力や共通時計の記録がない旧セーブも、初回の `PUT /sync` で既存の時計移行を適用します。ローカルの月数を直接サーバーの維持費時刻と比較せず、資源・兵・武将・工事を保って共通時間へ基準を合わせます。移行自体では過去の収入・維持費・周回報酬を発生させません。すでに保存されている未移行セーブとの比較でも、体力・修復・維持費は同じ移行後の基準を使います。共通時計へ移行済みの保存を、時刻のない旧ファイルで巻き戻そうとした場合は `409 CLOCK_ANCHOR_REQUIRED` で拒否します。

フロントエンドには行動予定表、施設の絵札・16件の一覧表示、条件保存、最大3名の武将比較を追加しています。利用手順は[公開ガイド](../guide/)と[旧セーブの復元案内](../guide/data-recovery/#legacy-save)を参照してください。表示条件は端末側に保存し、これらの閲覧機能に新しいAPIやDB移行はありません。通常同期の通知方針、本人確認・役職・購入済み権利の検証、ゲームの費用と成長条件は既存の仕組みを使います。

## v5.2.0 派遣部隊の帰還と同盟部隊の移動

## v4.9.12 武将の体力

武将の人物IDごとの体力（0〜100）を保存・同期し、実戦の勝利で15、敗北で25を消耗させます。共通時間で1か月あたり10回復し、行軍中の参加武将は回復を待機します。通常攻城・支拠点・野良兵戦・対人戦・イベント・同盟の指揮軍団など、実際に参加する本人の武将を対象にします。

体力は既存のセーブと戦果の同じ更新で確定します。体力が欠けた旧セーブの送信、別ランクの絵巻、端末切替、報酬武将の復元で消耗が消えないように調停します。フィールドの武将由来の戦力にも共通の体力係数を使い、行軍では出発時の参加者と能力を保持します。共有天下統一など個人武将が参加しない戦闘は対象外です。

## Ver.4.9.10 — 兵・施設の維持費、輸送兵の独立受入枠とおまかせ配置

共通エンジンで、現在の所有兵数から金銭・兵糧の維持費、完成済み施設と城郭のレベルから4資源の施設維持費を計算します。`income()` の通常4キーは生産から維持費を差し引いた純収支で、`gross`、`troopUpkeep`、`facilityUpkeep`、`totalTroops` に内訳を返します。既存の60秒／月の時間積分、端数繰越、資産0下限を使い、月境界で重ねて課金しません。

追加移行 `0033_external_troop_upkeep` は、空城・交易・同盟にある本人の兵の合計と変化時刻を保存します。移動・所有権変更・損耗の元の確定処理と同じトランザクションで更新し、既存の空城駐留・交易預託・同盟部隊は削除しません。外部の兵の課金は移行時の共通時刻から始め、それより前の期間には遡及しません。

本人の同期応答に `maintenanceAuthority` を追加し、`PUT /sync` は同じ台帳の `maintenanceRevision` を送信します。共有時計と外部保有数の両方が確認できた時刻まで進め、後から来た通知で過去の残高を再計算しません。古い版や競合した台帳のまま書き込もうとした場合は、最新の保存へ同期してから再試行します。私有の外部兵数は公開プロフィールには含めません。

兵士交易の純増受領・返還と空城からの帰還には、共通エンジンの `troopTransportCapacity()` を使います。通常の募兵容量には依存せず、本隊の既存保有上限1億人から進軍中の兵を除いた枠で受け入れます。兵数の所有上限と、交易1回の数量上限100万人を分けています。空き城一覧の `army.capacity` は互換用の受入上限、`transportCapacity` は同値、`recruitmentCapacity` は通常募兵容量です。

`POST /branches/auto-assign-commanders` は通常の支拠点操作の封筒と `branchId`（実在する支拠点IDまたは `all`）を受け取ります。未配置武将のみを空き枠へ割り当て、既存配置と資源・指令を保ちます。厳密な要求ハッシュに自動配置の操作と対象を含め、既存 `branch_deployment_requests` の `assign-commander` 分類で結果を原子的に記録します。自動配置自体には新しいテーブルは使いません。

### ブラウザ通知の設定と定期配信

通知は初期状態で無効です。利用者が「保存・設定 → 通知設定」でブラウザの許可を取り、端末を登録して有効にします。1人5端末まで、合戦・書状・作戦・普請／研究・イベントを個別に選択できます。既定の休止時間は日本時間22時〜8時、最短間隔は5分です。間隔は0・5・15・60分から選べ、0も次の配信処理で送信します。

APIの実行環境へ以下を設定します。鍵や実際の値はソース・README・公開フロントエンドへ保存しません。

| 実行時変数 | 内容 |
| --- | --- |
| `WEB_PUSH_PRIVATE_JWK` | P-256署名鍵の秘密JWKをJSON文字列で保存する秘密変数。 |
| `WEB_PUSH_PUBLIC_KEY` | 対応する非圧縮65バイト公開鍵のbase64url表現。ブラウザの購読に使用。 |
| `WEB_PUSH_SUBJECT` | VAPIDの連絡先となる `mailto:` またはHTTPS URL。 |

`web-push.js` はWorkerのWeb CryptoでRFC 8291の `aes128gcm` 暗号化とRFC 8292のVAPID署名を行います。既知のpushサービスのHTTPS endpointだけへ送り、リダイレクトを拒否します。通知本文は一般的な件名に限り、書状本文や作戦内容を載せません。

[`.github/workflows/notifications.yml`](../.github/workflows/notifications.yml) が `2-57/5 * * * *` の5分間隔で、設定済みのAPI URLへ `POST /notifications/tick` を送ります。APIの配置先を変える場合はworkflow内の `NOTIFICATION_TICK_URL` も更新します。Actionsのscheduleを有効にし、必要時には `workflow_dispatch` でも起動できます。この経路に領主トークンやVAPID秘密鍵を渡す必要はありません。通常のAPIアクセス時の `ctx.waitUntil` も配信を補助します。

1回のtickは最大30人をcursorで巡回し、最大6人×5端末を並列処理します。1件のまとめ通知は最大8件です。起動は60秒のDBガードで制限し、HTTP側も1分2回までです。GitHub Actionsの実行待ち、対象人数、端末やpushサービスの状態によって配信は遅れるため、5分以内の到着は保証しません。

配信前にoutboxを原子的に取得し、暗号化の後にも設定世代・休止時間・カテゴリ・BAN・端末登録・同盟所属・作戦状態・未読状態を再確認します。完成通知は通常の成功した保存と同じtransactionでも記録し、tick間に工事が `jobs` から消えた場合に対応します。失敗時は再送待ち、404/410は端末登録の削除とし、同じ通知の二重取得を防ぎます。一般の古いoutboxは7日を目安に掃除し、普請の配信済み記録は長期オフライン中の再通知を防ぐため保持します。

`test-notifications.mjs` は実際の移行SQLを使用し、暗号文の独立した受信処理での復号、VAPID署名、配信設定・同時実行・取消・保存競合を検証します。テストの外部pushはfetch mockで置き換えます。

以降の旧バージョンの説明は導入時の背景です。現在の配備確認には冒頭の4.4.0と最新の移行一式を使用してください。

## Ver.3.23.0 — 同盟・運営チャットの音声通話

`voice.js` は同盟ごとの音声ルームと運営・スタッフ専用音声ルームの認証済みシグナリングを提供します。ブラウザ同士の音声はWebRTCで送受信し、WorkerやD1に音声・映像を保存しません。1部屋8人、1アカウントにつき1セッションです。別端末で参加すると旧セッションが失効します。

### APIと期限

- `GET /voice/room?channel=guild|admin`：許可された部屋の参加者のみを取得します。
- `POST /voice/join`：`channel,muted` を送り、サーバー発行の `vc_` セッションID、参加者、ICE接続設定、更新間隔を受け取ります。
- `GET /voice/poll?sessionId=...&after=...`：本人宛ての未読SDP・ICEと最新の参加者を取得します。
- `POST /voice/heartbeat`：`sessionId,muted` で参加を延長します。必要なTURN接続設定も更新します。
- `POST /voice/signal`：`sessionId,toSessionId,kind,payload` を送ります。相手が同じ部屋の有効な参加者であることを確定時に確認します。
- `POST /voice/leave`：自分のセッションのみを終了します。終了済みの場合も安全に完了します。

通常の更新は2秒、参加の延長は10秒、延長が途切れたセッションは45秒で失効します。SDP・ICEは60秒で期限切れとなり、参加・延長時の件数制限付き掃除で削除されます。宛先が受領済みの信号には短い重複排除期間を設け、応答紛失後の再送で古い交渉を繰り返さないようにします。SDPは単一の音声メディアだけを許可し、映像・データチャネル、過大な内容、別の部屋への信号を拒否します。

### 認可・表示・切断

全操作で、本人の認証、利用停止世代、運営・スタッフの任期、同盟の所属世代を確認します。所属変更のトリガーが世代を増やすため、脱退後の再加入でも旧セッションは復活しません。参加人数の判定と参加処理、信号の送受信はSQLの確定条件で保護し、非同期処理の途中で参加資格や名簿が変わった場合も再確認します。

名簿に返すのは通話セッションID、現在の表示名、公開官職、ミュート状態、参加日時、自分かどうかです。プレイヤーIDや運営・スタッフの権限フラグは返しません。ブラウザは失効を確認するとマイク・音声再生・接続・タイマーを終了します。音声の通話部分は参加者間の接続なので、ゲーム外で改変したクライアント同士の通信をサーバーから物理的に停止する機能ではありません。

### 任意のTURN中継設定

未設定時は `stun:stun.cloudflare.com:3478` を使用します。直接接続できないネットワーク向けの中継は、別途運用するTURNサーバーの以下のランタイム設定で有効にできます。CoturnのTURN REST方式と同じHMAC方式を使用します。

| 変数 | 値 |
| --- | --- |
| `VOICE_TURN_URLS` | TURN URLのJSON配列、またはカンマ・空白区切り。最大5個。`turn:` / `turns:`、UDP / TCPの指定に対応。 |
| `VOICE_TURN_SHARED_SECRET` | TURNサーバーと一致する24文字以上の共有シークレット。秘密変数として保管します。 |

共有シークレットはクライアントへ返しません。有効期限とランダムなセッションIDをユーザー名にした短期HMAC資格情報だけを返します。約1時間の資格情報を10分単位で更新し、ハートビートの応答を受けたブラウザが接続設定を差し替えるため、既存の通話をつなぎ直さずに次の接続回復へ備えます。これらの環境変数が未設定・不正な場合は中継を有効にせず、STUN設定を返します。

`test-voice.mjs` は実WorkerとSQLiteで、部屋分離、同時参加の定員、権限の失効・復帰、BAN、確定時競合、信号検証、期限、TURN資格情報を検証します。`tests/test-voice-api.cjs` と `tests/test-voice-controller.cjs` はブラウザ側の認証と媒体の解放を確認します。配置時は音声通話の移行を適用し、`GET /health` の `version:"3.23.0"` と `features.audioCalls:true` を確認してください。

### 大都市の支拠点と攻城順序

支拠点は親となる都市の北・東・南・西に配置する個人の付属施設です。江戸は4か所・各Lv.8、二条・大坂・名古屋は各2か所・各Lv.24を上限とし、京都御所には設置しません。独立した領地や占領数・周回報酬には加算しません。江戸の各支拠点は6種類、二条・大坂・名古屋の各支拠点は12種類の施設枠を持ち、完成した施設だけが生産・兵数上限・その支拠点の防衛に効果を与えます。完成済みの施設Lvは、その支拠点の完成済みLvまでです。

`0020_branch_states.sql` の `branch_states` と `branch_requests` が配置・完成レベル・陥落状態・工事の絶対完了時刻を管理します。`GET /branches` は本人の `campaignId`・`sequence`・`branchState`・親都市別の状態と通常の同期応答を返します。`POST /branches/build` は `parentCastleId,direction`、`POST /branches/upgrade` と `/branches/repair` は `branchId` を指定し、共通で `requestId,campaignId,sequence,deviceId,expectedRevision` を付けます。失われた応答の再試行は同じ操作番号と元の物語・操作番号を保持します。費用・指令・同時普請枠・時間を共通エンジンで計算し、現在の親都市の領有、江戸の権限、役職、操作権と台帳を確定時にも照合します。

支城本体の建設・増築と内部施設の建設・増築は、支城ごとの受付順に1件ずつ進みます。すでに工事中の支城には、残りの指令と資源の範囲で次の普請を予約できます。支城ごとに通常の普請枠を1枠使い、ほかの支城は別の空き枠で同時進行します。1件を受け付けるたびに資源と指令1を支払い、同じ受付番号で照会・再試行したときは重ねて支払いません。

施設の新設は `POST /branches/build-facility`、増築は `POST /branches/upgrade-facility` に `branchId,facilityId` と共通項目を送ります。各注文は1段階分です。施設の建設を予約した後は、その施設の増築を続けて予約できます。直前までの予約が完了した時点の本体レベルが施設の上限になります。たとえば本体Lv.1の建設に続けて、施設Lv.1の建設、本体Lv.2の増築、同じ施設Lv.2の増築をこの順で予約できます。施設の工期はその注文の開始Lv.0〜7が60秒、Lv.8〜15が120秒、Lv.16〜23が180秒です。

`branchState.jobs` は着工中と着工待ちを含み、同じ支城IDの配列順が実行順です。施設ジョブは `kind:"branch",id:支拠点ID,facilityId:施設ID` を持ちます。既存の工事の絶対完了時刻 `completesElapsedMs` を保ち、新しい注文は先行工事に続く完了時刻を持ちます。時間停止中は新規注文を受け付けません。陥落時はその支城の未完了の普請をすべて取り消し、支払い済みの資源・指令は返却しません。修復は1件だけ受け付け、修復完了後に次の本体・施設の普請を予約できます。

6種類の基本施設は田畑・商家・伐採所・採石場・兵舎・物見櫓です。他の大都市では兵糧蔵・交易港・製材所・石工場・訓練場・堀の6種類を追加します。施設レベルは支拠点ごとの `facilities` に保存し、旧セーブの未設定項目はすべて未建設として扱います。無料の施設・資源・兵は配布しません。生産効果は通常城下の技術補正後に定額を加算し、兵舎・訓練場は兵数上限のみを増やします。物見櫓はその支拠点の防衛をLvごとに1%、堀は0.75%高め、堀の効果は攻城技術・攻城戦法で軽減します。陥落するとすべての施設効果が停止し、完成レベルを保ったまま支拠点の修復完了で復帰します。

施設の各段階の完成時刻は `facilityCompletedAt` に保存します。遠隔の攻城で施設の完成だけが先に確定した場合も、遅れて追いつく保存の生産に過去へ遡って加算しません。この履歴・施設レベル・施設工事も通常アップロードからは採用せず、支拠点台帳から復元します。操作台帳の既存 `action` 列は建設・増築の区分を維持し、施設の具体的な操作と対象はリクエストハッシュと `result_json.facilityId` に記録するため、支拠点本体と施設の間でも操作番号の使い回しを拒否します。追加のスキーマ移行はありません。

一般の `/sync` は、アップロード内の支拠点と支拠点工事を正として採用しません。直前のサーバー保存と支拠点台帳から、実際の共通時刻までのCPU戦をサーバー側で計算し、確かめられた陥落だけを台帳へ反映します。アップロードの乱数や陥落フラグは今回の戦闘の証拠に使いません。親都市の領有について予測が食い違う場合、サーバー上で保持している親都市と支拠点は消さず、その領有だけを補正します。サーバーのCPU計算で親都市を失っても、個人側の進行が領有を維持している場合は、CPU落城の直前に記録した正確な陥落済み支拠点と有効な有料工事を残します。以前の未陥落状態や中止した増築へ戻しません。双方の進行で親都市の喪失が確認されたときに支拠点を取り除きます。

この補正は親都市・支拠点と本拠の整合性に限り、個人側の資源・武将・研究などの進捗を置き換えません。本拠の所在・領国喪失・統一状態・時間進行を補正後の領有から再計算するため、同じ保存が繰り返し拒否されることもありません。現在の役職で認められない領有や、別の領主の領有を付与することはありません。普請の完了はサーバー共通時間に固定し、個人の保存時刻を早めても完成は早まりません。PvPで親を失った支拠点とその工事は、引き続き同じ攻城トランザクションで取り除きます。周回では本拠以外の付属施設を持ち越しません。

`branch_states.resolved_elapsed_ms` は、その物語の支拠点についてサーバーが確定済みの共通時刻です。時間だけ進み状態や工事が変わらない場合は `sequence` を増やさないため、送信待ちの普請操作を通常同期で無効にしません。保存版・台帳版・この確定時刻・役職・共通時計を同じトランザクションで照合します。個人用の同期応答に `branchResolvedElapsedMs` を返し、ブラウザーは認証済みの同じアカウント・物語の応答だけをエンジンの実行時権限へ渡します。セーブJSONからこの権限を復元しません。

PvPの陥落が守備側の古い保存位置より後に発生した場合、その陥落を過去のCPU戦へ適用して親拠点を落としてはいけません。確定時刻以前の支拠点付き都市へのCPU襲撃は再実行せず、その後の襲撃から進めます。この時刻は物語全体の支拠点に共通なので、一都市のPvP更新後に別の支拠点付き都市へ過去のCPU被害を追加することもありません。支拠点のない都市の通常進行は変えません。未来5秒以内の通常保存が届いても、支拠点の確定時刻は実際のサーバー時刻を越えず、その後の本来のCPU襲撃を飛ばしません。

大都市の本城を攻める前に、完成済みで未陥落の支拠点をすべて攻略する必要があります。`/field` の親都市は `branches` に各支拠点の名称・方角・レベル・陥落・普請状況・守備値・攻撃可否を返し、未攻略の支拠点がある本城の `attackable` を無効にします。`POST /field/attack` は親の `targetCastleId` に加えて `targetBranchId` を指定できます。支拠点戦の報告は `battleMode:"branch"` と `branchId,branchName,branchFallen` を持ちます。勝利は支拠点を陥落状態にし、進行中の増築を中止しますが、親都市の兵・資源・領有を変更しません。戦利品・勝利報酬・別の城の占領・戦闘数や勝利数による評価・目標達成は増えず、攻撃側は通常の指令・兵糧・戦闘損失を負担します。

陥落した支拠点は完成Lvを保持し、有料の時間制の修復が完了してから防衛へ戻ります。修復中は本城の攻撃を妨げません。京都御所から江戸へ攻めるための在任中の天皇の条件は、江戸の支拠点攻撃にも適用します。派遣部隊の本城への反撃も支拠点を飛び越せません。戦闘・修復・同期が競合すると、保存版と支拠点版が一致した一件だけが確定します。

`test-branches.mjs` は建設・増築・修復・再送・制限を、`test-branch-sieges.mjs` は工事完了の表示、本城攻撃の順序、陥落・修復、保護城、輸入データ、同時攻撃、途中失敗、反撃の迂回防止をローカルAPIで検証します。`test-branch-sync.mjs` はCPU陥落の通常同期、親拠点喪失の証拠、古い領有・未来時刻・陥落偽装、PvP後の時間順序、状態不変時の操作番号、確定時の競合とロールバックを検証します。

## 保存と同期

ユーザー、トークンのハッシュ、同盟、フレンド、メッセージ、お知らせ、郵便、ギフト受取記録、クラウドセーブ、操作権、端末連携コード、接続状況、共通時計をD1へ保存します。

同じ領主IDにつき一つの操作権リースを持ち、セーブの版番号による比較更新を行います。同時操作による上書きを防ぎ、別端末へ切り替えた場合は古い端末の書き込みを拒否します。連携コードは一回限り・10分間有効、サーバーにはハッシュだけを保存します。連携後には新しい端末用のトークンを発行します。

運営権限はユーザー行、スタッフ権限は現在の任命記録で確認します。江戸城・德川家康Uは運営だけ、京都御所はスタッフだけが所持できます。旧バージョンの役職と合わない保存は、通常の本拠と成長を保てる形に移行します。運営のU復元は重複しません。

城郭の強化上限は、京都御所がLv.128、江戸がLv.64、二条・大坂・名古屋がLv.48、通常城がLv.32です。保存、普請、公開フィールド、費用と効果を同じ上限で扱います。城下町施設はLv.32を維持します。

運営とスタッフの家名は「德川家」です。家名から役職を判定せず、江戸城・専用Uは運営資格、京都御所は現在のスタッフ資格で確認します。任命前の個人の家名はサーバーのバックアップを正とし、解任後の本拠・所有城・公開プロフィールへ復帰させます。通常の「徳川家」は一般プレイヤーが利用できます。

## 他領主との交易（Ver.3.10.0）

`0011_player_trades.sql` は、金銭・兵糧・木材・石材・勾玉の輸出入を扱う提案、実行記録、受取台帳を追加します。相手は領主IDで指定し、家名や城IDが同じでも別の領主として扱います。提供資産は提案時に送り主の保存から差し引いて預かります。相手の承認時に、承認者自身の保存から対価を差し引き、提供資産を加えます。対価なしの無償輸出もできます。

送り主への対価と、取消・拒否による返金は独立した受取台帳に残し、本人が「受け取る」を実行したときにだけ本人の保存へ加算します。相手の保存・revision・操作権は一切変更しません。相手がオンラインで未保存の進行を持っていても、その進行を交易によって巻き戻すことがありません。資産上限を超える場合は全額受取を拒否し、台帳を残します。切り捨てや資産消失はありません。

提案・承認・取消・拒否・受取はすべて現在の操作端末と保存revisionを検証します。各資産は1件あたり最大1,000,000、所有上限は資産ごとに100,000,000、承認待ちの送信は20件までです。指令・手数料は不要で、共通時計が停止中でも操作できます。成功したrequestIdと意味上の内容を永続化し、同一要求の再送では同じ実行記録と最新の同期結果を返します。同時の承認と取消、二重受取、途中失敗を、条件付き記録とD1バッチでまとめて処理します。既存のメールギフト適用関数は使いません。

閲覧できるのは当事者二人だけです。提案・対価・返金は同盟離脱、役職変更、周回、新しい物語を越えて同じ領主IDに保持されます。各APIとDTOは `API_CONTRACT.md` の「Player trades」を参照してください。

`GET /trades` の一覧は `box=incoming`（受信）、`outgoing`（送信）、`history`（両方向の履歴）、`claimable`（本人の受取待ち）を選べます。受取待ちは未受取の対価・返金だけを作成日時の新しい順に返すため、履歴の21件目以降に残る古い資産も直接探せます。全一覧で同じ件数制限・ページング・集計形式を使い、受取済みの記録は次の受取待ち一覧から外れます。

## 運営によるBAN・解除（Ver.3.11.0）

現在の `settings.adminUserId` 本人だけが、領主名・完全な公開IDで対象を探し、削除対象件数を確認してBANできます。スタッフや一般領主、入力JSONの権限指定には管理権を与えません。自分・運営本人は対象にできません。BAN中の一覧から解除でき、解除後は同じ領主ID・既存の接続トークンで再利用できます。

BANは一つのD1バッチで、本人が送った世界・同盟・フレンド・運営チャットと個人・同盟書状の本文行を削除し、接続表示・操作権・未使用の連携コードを停止します。計測中の歩行セッションも終了し、確定済みの歩数や報酬は保持します。本人が関係する承認待ちの交易を取消し、提供資産は元の送り主の受取待ち台帳へ返します。他人の本文、保存データ、資産、同盟所属・役職、確定済み取引は削除しません。解除しても消した本文は戻りません。

全端末の認証済み操作を `ACCOUNT_BANNED` で拒否し、BANと解除で進む認証世代をSQL更新時にも照合します。処理中の投稿・保存がBAN後に書き戻ったり、BAN→解除の間を跨いだ古い要求が通ったりすることを防ぎます。解除後の操作権と歩行計測は新たに開始します。公開の検索・接続一覧・共有地図・達成通知・写真はBAN中の対象を表示しません。

BANによる本文削除で `contentRevision` が進みます。チャット・書状はこの番号を返し、古い番号の差分取得には `reset:true` と最新ページを返します。クライアントは削除前の表示キャッシュを破棄して置き換えます。監査記録には運営・対象・操作番号・時刻・削除件数を保存し、削除した本文のコピーは保存しません。同じ要求の再送は元の記録を返すだけで再BAN・再解除を行いません。

APIの入力と出力は `API_CONTRACT.md` の「Account moderation」を参照してください。公開確認は `GET /health` / `GET /config` の `version:"3.11.0"` と `features.moderation:true` を読み取り、実プレイヤーのBANや投稿削除は行いません。

## 共通のループ時計

`GET /api/v1/world-clock` は認証不要です。サーバーの経過時間、進行中かどうか、速度、設定の版番号、サーバー時刻を返します。`PATCH` は運営のみ、版番号が一致した場合にだけ変更します。クライアントが任意の年月を送って世界時計を巻き戻す操作は受け付けません。

暦は672か月で一周し、1560年1月から1615年12月の後に次の周へ進みます。内部の経過ミリ秒は増え続けます。停止・再開や速度変更では、それまでに経過した時間を確定してから新しい設定へ切り替えます。

新しいセーブは `state.worldClock` に適用済みの経過時間を保存します。年月・月内秒との整合性と、サーバーより過度に未来でないことを検証します。移行済みのクラウドセーブを、時計位置のない旧形式で上書きすることはできません。古い有効な保存位置からの再接続は許容します。周回の境界は共通エンジンを使ってサーバー側で確定し、それ以外の進行は操作端末が共通時刻へ追いつきます。

## v3.6 — 拠点の集計・報酬・御触書

`0007_world_cycles.sql` は `player_saves` に周回の保存位置と最初の本拠を追加し、`cycle_receipts` と `achievement_events` を作成します。適用済みの0000〜0006は変更せず、追加済みのjournalと一緒に維持してください。

暦の境界では、その時点で所有する本拠以外の城1つにつき、勾玉100・金銭1,000・兵糧1,000を一度だけ加算します。通常の所持上限は適用されます。追加の領地は初期配置へ戻し、最初の本拠を復元します。運営は德川家・江戸城・専用Uを維持します。本拠の城郭レベル、施設、武将、技術、資源、同盟と共有金庫は引き継ぎ、本拠以外の城郭拡張と前の区切りから続く同盟・偵察を終了します。導入時点より前の周回報酬は遡って付与しません。

操作端末は境界の1ミリ秒前まで進めた保存を確定してから `POST /api/v1/sync/settle` を呼びます。通常の読み取りは、有効な操作権を持つ端末の未保存操作を先回りして集計しません。切断済みの保存は読み取り時に段階的に追いつきます。保存の版、操作権、共通時計、運営資格を更新時にも確認し、セーブ・報酬受取記録・通知を一つのD1バッチで確定します。再送や同時処理による重複付与、途中失敗時の部分的な加算を防ぎます。

公開の `GET /api/v1/achievements` は、受け入れ済みの保存やサーバーで確定した進行から、「どの領主が何を達成したか」を新しい順に返します。城の占領、領有数の節目、施設・研究の成長、任務達成、統一、占領報酬などが対象です。最初に読み込んだ保存から過去の通知を作ることはありません。通知キーで再送をまとめ、非公開のログイン履歴、端末情報、トークン、資産総額、金庫台帳は含めません。

### 共通エンジンの同梱

`game-engine.js` はフロントエンドの `engine.js` と同一です。`game-officers.js` は `officers-data.js` のグローバル参照だけを `window.` から `globalThis.` へ変更したものです。`game-runtime.js` が両方を読み込み、APIとテストへ公開します。独立した手計算で生産・普請・研究・CPUの動きを再現せず、同じ決定的エンジンを再利用します。エンジン更新時はこれらのコピーを同期し、`build-worker.mjs` で全依存を含む配備用ESMを生成します。ビルドはNode.jsで行いますが、本番WorkerにはNode.js依存がありません。

`test-world-cycles.mjs` は、周回をまたぐ同時更新、最後の占領と定期同期の競合、操作権交代、受取記録の再送、公開通知とページング、長期間の再接続、ロールバック、旧保存、運営・解任時の制約を、メモリー内のDBだけで検証します。

## 接続一覧とプライバシー

端末は約20秒ごとに接続を確認し、90秒以内に確認できた領主をオンラインとします。同じ領主の複数端末は集約します。公開一覧は表示名・公開ID・所属と現在の官職を返します。管理権限のフラグ、IPアドレス、トークン、内部端末IDは公開しません。

## 総合評価と位階

全プレイヤーへ、領地・城郭、完成済み施設、所持武将、軍団と奉行、研究、威信・攻城の勝利実績、歩行進捗を合計した10万点満点の総合評価と、無位から正一位まで17段階の位階を表示します。位階は称号であり、運営・スタッフ・同盟の権限には影響しません。共通の `GameEngine.publicEvaluation` を使い、クライアントから送られた評価値や称号は採用しません。

公開DTOは基本を `evaluation` とし、盟主・戦報・書状等は表示する人物に対応した評価を添えます。チャットと書状の読み取りは `playerEvaluations:[{playerId,evaluation}]` も返し、追加発言がなくても表示済みの参加者の称号を更新できます。対象はその部屋・書状の参加者と最近の発言者に限り、非公開の会話を越えて取得しません。詳細なフィールド名は `API_CONTRACT.md` に記載しています。

評価は最新の正規保存に現在の役職、完成した共同施設、未反映の周回を読み取り専用で投影します。評価の取得だけで月次進行・報酬付与・保存・編成変更はしません。未保存の領主は0点・無位ですが、保存を正常に読めない場合や取得できない過去の人物は `null` とし、未確認の位階を表示しません。同じ応答内の領主はまとめて一度ずつ計算し、DBの移行や称号キャッシュは追加しません。`test-evaluation.mjs` で役職・共有拠点・周回・差分更新・履歴・100人一覧の重複計算防止を検証します。

## サポートスタッフ

スタッフは `staff_members` に保存し、`isStaff` と `isAdmin` を区別します。主運営のみ `GET/POST /admin/staff` を使用でき、登録済みの対象領主を任命・解任できます。役職変更と再送台帳は同じトランザクションで確定します。解任後に古い任命要求を再送しても、役職を巻き戻しません。

スタッフの追加権限は、京都御所の共同普請、運営チャットの閲覧・送信、直近24時間のログイン・接続履歴の閲覧です。江戸城・德川家康U・共通時計の管理・告知・配布・スタッフ管理には運営権限を要求します。運営とスタッフを兼ねる場合は運営の德川家・江戸城を優先します。運営チャットとログイン履歴はSQLでも参加権限を再確認し、解除済みのトークンで利用できないようにします。任命・解任で領主IDや認証トークンを作り直すことはありません。

### 京都御所の共同成長

京都御所は占領できない固定本拠です。対人の報酬戦は受け付け、実際の共有施設を守備計算に使います。相手が勝利しても守備側の兵・資源・施設は減らしません。城郭レベル、城下町の64施設、進行中の普請をサーバーで一つに管理し、全スタッフが共有します。武将・軍団・研究・奉行・資源残高は個人ごとに保持し、着工者が自分の資源と指令を使います。共有した成長は周回を越えて残ります。

`GET /staff/base` と同期応答の `staffBase` は個人セーブとは独立した版番号を持ちます。`POST /staff/base/upgrade` は個人セーブの版、共同拠点の版、端末の操作権、現在のスタッフ資格を確認し、個人負担・共同の着工・再送記録を一緒に確定します。クライアントのインポートや通常保存から共有レベルを書き換えることはできません。

共有施設は実行中のゲームへ投影し、個人セーブの施設とは分けて保存します。任命前の個人拠点をサーバーに記録し、解任後は個人の進行を維持して通常の本拠へ戻します。共有普請の完成時刻を使って留守中の進行を区切り、新しい施設効果を完成前の期間へさかのぼって加算しません。

## 領主アイコンと同盟資産

領主アイコンは本人だけが登録・削除できます。ブラウザー側で切り抜いた256×256 JPEGを受け取り、Workerで48KiBの上限と構造を検証し、EXIF・GPS・コメント等を除去します。画像本体はR2、現在版のメタデータはD1へ保存します。画像更新中の読み取り・削除競合を検証し、古い画像や削除済み画像は404で返します。

同盟は盟主・副盟主・メンバーの役職を持ちます。5種類の共有資産の移動は、現在の所属、操作端末、プレイヤー保存の版、金庫と共通時計の版をトランザクション内で検証し、金庫と所持資産を一緒に更新します。成功済みrequestIdを保存し、応答を失った後の再送を再加算しません。台帳は所属メンバーだけが取得できます。公開ランキングは総威信・人数・領有城を集計し、金庫の残高や台帳を含めません。

追加検証は `test-recent-logins.mjs`、`test-avatars.mjs`、`test-avatar-jpeg.mjs`、`test-clans.mjs`、`test-guild-assets.mjs`、`test-guild-roles.mjs`、`test-guild-icons.mjs` です。JPEGの復号比較はPythonのPillowも使用します。

## 実装上の境界

SQL値はバインドします。各prepareは一つのSQL文、複数操作のトランザクションは `DB.batch()` を使います。セーブとギフトの受取台帳はクライアントでも同時に永続化し、再送時の重複を防ぎます。

Cookieは使用せず、非公開APIにはゲームのBearerトークンが必要です。CORSは正確な許可Originだけに応答し、資格情報付きワイルドカードを使いません。秘密の環境変数、運営キー、生トークンをログに出力しません。
